# 项目提取

从已有的网站、代码库、设计系统或一组作品里归纳 Template。原则是只记录看得到的东西：每个值都要说得出从哪里来，看不出来的地方留成缺口，不凭空补。

## 取值顺序

按可靠程度依次取，前一层有的值，后一层只用来核对：

1. **现成的设计文档和 token 文件**：例如 `DESIGN.md`、设计规范、token JSON、Tailwind 或其他主题配置、Figma 导出的变量。它们是作者写下的意图，最可靠。
2. **代码里的值**：CSS 变量、组件里实际用到的颜色、字号、间距、圆角和阴影。文档与代码不一致时，两个值都记下；只有会进入 Seed 或 Template 的那几项才问用户以哪个为准，其余以设计文档为准，只记录。
3. **运行起来的页面**：截图或直接看用户已经打开的页面，用来归纳文法（网格、对齐、层级、留白、装置、状态），值以前两层为准。

项目全程只读：不改文件，不装依赖，不构建。要把项目跑起来才能截图时先问用户；用户给了线上地址或已经在运行的地址，可以直接看。还看不到页面时，先只凭前两层写报告：文法各条都记为推断，节首写明「没有目视核对」，把看页面列为要问的问题。一组作品（图片、PDF）只有第 3 层，值都是推断的。

**来源的适用范围**：来源只覆盖某些表面时（例如设计文档只写了应用界面，用户却要海报和落地页），在报告开头写明，并问用户这份来源能不能代表要做的场景，或者另有规范要一起看。画布、断点、展示字号这些场景值在来源里没有依据时，都是缺口。

## 提取报告

落成 Seed 和 Template 之前，先写一份提取报告给用户确认。报告写在对话里或用户风格目录旁的草稿文件里，不进 `musekit/<id>/`。

报告开头写拟定的标识：`id`、中文名、英文名、`family`、`mood` 和要声明的场景，各附依据，由用户一并确认。之后分四节：

**1. 来源**：读了哪些文件、看了哪些页面，各自对应第几层。没读到的层也写一句（例如「项目没有 token 文件」）。

**2. 值**：按 Seed 类别列表，每个值归入三类之一。画布、断点、场景字号不属于任何 Seed 类别，列在表尾的「场景覆盖」里。

| 类别 | token | 值 | 归类 | 出处或依据 |
| --- | --- | --- | --- | --- |
| color | `paper` | `#FAFAF7` | 取到 | `tokens/color.json` 的 `surface.base` |
| color | `ink-muted` | `#5C5C57` | 推断 | 代码里次要文字有三种灰，取用得最多的一种（`Card.css`、`List.css`） |
| typography | `size-display` | — | 缺口 | 项目只有界面字号，没有展示层级 |

- **取到**：值原样出自文件。写明文件和键名，或文件和行；项目的名字与 Musekit 角色名的对应（例如项目的 `text-secondary` 对应 `ink-muted`）也写在出处里，不因此改记为推断。
- **推断**：值经过计算、统计或挑选。写明依据，例如「出现次数最多」「从截图量得」「由两个取到的值算出」。项目有多级刻度而 token 只收一个值时（例如四级圆角、四级阴影只对应 `radius`、`shadow`），挑一个代表值记为推断，完整刻度写进 Seed 的要点。
- **缺口**：写明打算怎么补，三选一：问用户；沿用某个库内 Template 的做法（写明是哪一个、沿用哪几项）；这个场景不声明。

成对的浅色和深色值单列一张表，标明它们将成为颜色 Seed 的 `light` 和 `dark` 两个变体。

**3. 文法**：按 Template 的 `## 文法` 各条（网格、对齐、层级、留白、色彩、装置、图像、状态）写一句归纳，每句附依据（哪个页面、哪个组件）。看不出来的条目同样写成缺口。

**4. 与风格库的对照**：

- 每个类别：与哪个库内 Seed 的值一致，可以直接引用；不一致的，要另写用户 Seed。
- 字体：每个字体是否在注册表里（`muse.py list fonts`），以及要用的字重在不在它的加载地址里。系统字体（注册表里 `kind: system`）和没登记的版权字体都按版权字体处理，先问用户有没有授权。没有授权、不在注册表里，或字重加载不到的，写出打算换成的字体、字重和差异；差异会削弱风格辨识时（例如项目靠细字重立住标题），写明后果，并让用户选：接受替换，或等维护者把原字体登记进注册表。
- 间距：项目的间距阶梯到不了海报和网页的边距时（`margin`、`gutter` 必须取自阶梯），把补到哪一级列为缺口。
- 打算声明的场景，以及每个场景有没有足够的依据写场景适配。
- 精神：一段话，说明这套风格要解决什么阅读问题。依据不足时写明是推断。

完成标准：每个值都已归类，缺口都有处理方式，用户已确认，或改过后确认。

## 落成

用户确认报告后才写文件：

- 取到和推断的值进 Seed；用户回答过的缺口按回答写，沿用的写明沿用了谁。
- 推断的规则在 Template 正文里也照实写，例如「项目里看不出状态的做法，沿用 neo-swiss」。
- 报告不随 Template 交付；交付说明里列出推断的值和沿用的部分，方便用户以后核对。
