# Web Design

把用户要完成的任务组织成可用、清楚、有辨识度的界面，并交付可运行的代码。用户只要设计方向或方案时，按其范围交付。全程守住[底线](../../references/critique.md#底线)。

## Brief → 风格 → 结构 → 实现 → 评审

1. **写 Brief。** 先读现有项目：页面、组件、技术栈、设计系统和项目规则。然后回答：
   - 谁来，进入页面后要看懂什么、完成什么。
   - 主操作是什么，完成后给出什么反馈。
   - 涉及哪些状态：加载、空、错误、选中、完成。
   - 目标视口：至少一个桌面宽度和一个手机宽度。
   - 怎样算成功：2–3 条可以检查的标准，其中至少一条是走通一条任务路径。

   缺少必需事实时询问用户；用户要求直接做时，可以创作的内容（项目、日程、文案）标为示例，不能编造的事实（网址、电话、价格、身份）留空，并在交付里列出。完成标准：每个问题都有答案、标为示例，或列为待补。
2. **取风格。** Brief 写完后再取，用户点名了风格也一样：变体和约束要从 Brief 里来。项目已有设计系统时，把它交给 `musepool` 整理成 `source: user` 的风格，已有的组件契约优先；否则带上场景 `web`、Brief 里的气质与约束调用 `musepool`。得到作品目录里的 `style.md`，按[使用 style.md](../../references/style.md)使用。完成标准：`style.md` 已写出。
3. **选结构并用文法排它。** 从[页面原型](references/structures.md)中按任务选一个或组合几个，列出区域和使用顺序。再按 style.md 的文法和本场景适配，为桌面和手机分别决定每个区域的栏位、对齐轴、层级和重排方式。完成标准：每个视口都写出区域与栏位分配。
4. **实现。** 沿用项目的技术栈和组件。接入 style.md 的 `:root` 变量（项目已有 token 体系时做映射），加载字体，并按[界面方法](references/methods.md)处理真实文字、状态与动效。完成标准：页面在本地运行，主任务路径可以操作。
5. **评审。** 按[评审循环](../../references/critique.md#评审循环)检查，本媒介的清单是：
   - 在浏览器中走通主任务，桌面宽度和手机宽度（如 375px）都看。
   - 键盘能到达所有操作，焦点可见；状态不只靠颜色区分。
   - 字体加载后检查长标题、长数字和中文断行。
   - 动效承载信息时，在 reduced-motion 下仍然能理解。
   - 状态切换（出错、完成、展开）后截图确认实际渲染结果，不只检查 `hidden`、`aria-*` 这类属性。

   完成标准：最后一轮评审没有实质问题。

## 交付

交付代码、查看入口和 `style.md`。说明走通了哪条任务、检查了哪些视口和状态，以及风格状态（`draft` 时写明）。浏览器或运行环境不可用时，交付现有代码并写明没有做视觉验证。

完整的判断过程见[制作示例](references/examples.md)。
